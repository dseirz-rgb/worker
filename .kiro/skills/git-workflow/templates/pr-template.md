# Pull Request 模板与指南

> 规范化的 PR 流程是代码质量的重要保障

## 📋 PR 描述模板

```markdown
## 📝 变更说明

<!-- 简要描述这个 PR 做了什么 -->

## 🔗 关联 Issue

<!-- 关联的 Issue 编号 -->
Closes #

## 🎯 变更类型

<!-- 勾选适用的类型 -->
- [ ] ✨ 新功能 (feat)
- [ ] 🐛 Bug 修复 (fix)
- [ ] 📝 文档更新 (docs)
- [ ] 💄 代码格式 (style)
- [ ] ♻️ 代码重构 (refactor)
- [ ] ✅ 测试相关 (test)
- [ ] 🔧 构建/工具 (chore)
- [ ] ⚡ 性能优化 (perf)

## 📸 截图/演示

<!-- 如果是 UI 变更，请附上截图或 GIF -->

## ✅ 自检清单

- [ ] 代码已通过 lint 检查
- [ ] 已添加/更新相关测试
- [ ] 所有测试通过
- [ ] 已更新相关文档
- [ ] 已在本地测试功能
```

## 🎯 PR 最佳实践

### 1. 保持 PR 小而专注

```
✅ 好的 PR
- 单一功能或修复
- 200-400 行代码变更
- 容易审查和理解

❌ 不好的 PR
- 多个不相关的功能
- 1000+ 行代码变更
- 难以审查和测试
```

### 2. 提供清晰的描述

**必须包含:**
- 变更的目的和背景
- 实现方案的简要说明
- 测试方法和结果
- 相关的 Issue 链接

### 3. 添加有意义的截图

对于 UI 变更：
- 变更前后的对比截图
- 不同状态的截图（加载中、成功、错误）
- 移动端和桌面端的截图

### 4. 自检清单

在请求审查前确保：
- [ ] 代码符合项目规范
- [ ] 没有遗留的 console.log
- [ ] 没有硬编码的敏感信息
- [ ] 错误处理完善
- [ ] 边界情况已考虑

## 🔄 CI/CD 验证指南

### GitHub Actions 检查

PR 创建后，CI 会自动运行以下检查：

| 检查项 | 说明 | 必须通过 |
|--------|------|----------|
| Lint | 代码风格检查 | ✅ |
| Type Check | TypeScript 类型检查 | ✅ |
| Unit Tests | 单元测试 | ✅ |
| Build | 构建验证 | ✅ |
| E2E Tests | 端到端测试 | ⚠️ 视情况 |
| Coverage | 代码覆盖率 | ⚠️ 视情况 |

### 查看 CI 状态

```bash
# 使用 GitHub CLI 查看 PR 状态
gh pr checks

# 查看详细日志
gh pr checks --watch
```

### CI 失败处理

1. **Lint 失败**
   ```bash
   npm run lint:fix
   git add .
   git commit -m "style: 修复 lint 错误"
   git push
   ```

2. **类型检查失败**
   ```bash
   npm run typecheck
   # 根据错误信息修复类型问题
   ```

3. **测试失败**
   ```bash
   npm test
   # 查看失败的测试，修复后重新提交
   ```

4. **构建失败**
   ```bash
   npm run build
   # 查看构建错误，通常是导入问题或类型问题
   ```

## 📦 部署验证

### Vercel 预览部署

每个 PR 会自动创建预览部署：

1. **查看预览链接**
   - PR 页面会显示 Vercel 部署状态
   - 点击 "Visit Preview" 查看预览环境

2. **验证功能**
   - 在预览环境测试新功能
   - 检查是否有控制台错误
   - 验证移动端适配

3. **性能检查**
   - 使用 Lighthouse 检查性能
   - 确保没有明显的性能退化

### 部署检查清单

- [ ] 预览部署成功
- [ ] 功能在预览环境正常工作
- [ ] 没有控制台错误
- [ ] 移动端显示正常
- [ ] 性能没有明显退化

## 👥 代码审查指南

### 审查者职责

1. **代码质量**
   - 代码是否清晰易读
   - 是否遵循项目规范
   - 是否有潜在的 Bug

2. **架构设计**
   - 实现方案是否合理
   - 是否有更好的替代方案
   - 是否影响现有功能

3. **测试覆盖**
   - 是否有足够的测试
   - 边界情况是否覆盖
   - 测试是否有意义

### 审查评论规范

```markdown
# 必须修改
🔴 [Required] 这里有安全问题，必须修复

# 建议修改
🟡 [Suggestion] 建议使用更简洁的写法

# 疑问
🔵 [Question] 这里的逻辑是什么意思？

# 赞赏
🟢 [Nice] 这个实现很优雅！
```

### 响应审查意见

1. **认真对待每条评论**
2. **及时回复和修改**
3. **解释你的决定**
4. **感谢审查者的时间**

## 🔀 合并策略

### Squash and Merge（推荐）

```
多个提交 → 合并为一个提交 → 合并到主分支
```

**优点:**
- 保持主分支历史清晰
- 一个 PR 一个提交
- 便于回滚

### Merge Commit

```
保留所有提交 → 创建合并提交 → 合并到主分支
```

**适用场景:**
- 需要保留详细的提交历史
- 大型功能分支

### Rebase and Merge

```
变基到最新 → 线性合并 → 合并到主分支
```

**适用场景:**
- 追求线性历史
- 小型修改

---

## 🗑️ PR 合并后清理

```bash
# 删除本地分支
git branch -d feat/my-feature

# 删除远程分支（通常 GitHub 会自动删除）
git push origin --delete feat/my-feature

# 同步本地分支列表
git fetch --prune
```
