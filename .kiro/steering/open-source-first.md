# 开源优先原则 (Open Source First)

## 核心原则

在开发新功能时，**必须优先寻找和使用开源方案**，而不是从头编写。

## 执行步骤

### 1. 先调研，后动手

在写任何代码之前，必须：
- 搜索 GitHub 上是否有现成的开源项目
- 评估项目的活跃度、Star 数、最近更新时间
- 阅读项目的 README 和核心源码

### 2. Fork 改造，而非重写

找到合适的开源项目后：
- **直接 Fork 或下载源码**到项目中
- **基于源码改造**，而非参考后重写
- 保留原项目的核心逻辑和架构
- 只修改必要的部分（如 API 替换、配置扩展）

### 3. 常见改造场景

| 场景 | 做法 |
|------|------|
| 云端 API → 本地 | 将 Groq/OpenAI 调用改为 Ollama |
| 添加新功能 | 在原有代码基础上扩展，不重构 |
| 配置定制 | 添加配置文件，不硬编码 |
| 集成到项目 | 作为子模块或独立服务 |

## 禁止行为

❌ 看了开源项目后，自己从头写一遍  
❌ 只参考思路，不使用源码  
❌ 在没有调研的情况下开始编码  

## 正确做法

✅ `git clone` 下载源码  
✅ 删除 `.git` 目录，作为项目的一部分  
✅ 在原有代码上做最小改动  
✅ 记录改动点，便于后续升级  

## 示例

```bash
# 正确：Fork LlamaFS 改造
git clone https://github.com/iyaja/llama-fs.git echo/sidecar/janitor
rm -rf echo/sidecar/janitor/.git
# 然后在源码上改造

# 错误：看了 LlamaFS 后自己写
# 创建 janitor/__init__.py
# 创建 janitor/classifier.py  ← 这是重写，不是改造！
```

## 适用范围

此原则适用于所有新功能开发，特别是：
- 文件处理、AI 集成等通用功能
- 有成熟开源方案的领域
- 需要快速验证的 MVP 阶段
